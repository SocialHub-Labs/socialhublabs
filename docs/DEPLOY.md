# Deployment and operations

SocialHub Labs is deployed as a **Cloudflare Worker with Static Assets only**, using `public/` as the asset directory. It has no executable Worker entrypoint, database or API endpoint. See [architecture](ARCHITECTURE.md) for design and data flow.

## Cloudflare Git deployment (recommended)

The canonical repository is [SocialHub-Labs/socialhublabs](https://github.com/SocialHub-Labs/socialhublabs).

1. Add `socialhub.win` as a Cloudflare DNS zone on the Free plan, if it has not been added yet. Before changing nameservers, copy any current DNS records required for existing services, including MX records.
2. In **Workers & Pages**, create a Worker from Git, grant the Cloudflare GitHub integration access to **SocialHub-Labs/socialhublabs**, and select the `main` branch.
3. Set the Worker name to `socialhub-labs`. Use the repository root. The project has no framework or frontend build step; leave its build command empty.
4. Set the deploy command to `npx wrangler deploy`. The checked-in `wrangler.jsonc` declares the static assets directory.
5. Deploy and check the temporary Worker URL.
6. Under the Worker's **Settings → Domains & Routes**, add `socialhub.win` as a **Custom Domain**. Make sure any DNS records that conflict with the custom domain route are removed or corrected.
7. When the custom domain works, you can disable the account-specific `workers.dev` route and Worker preview URLs if they are not needed.
8. Confirm Git builds are enabled for `main`, so that an ordinary push deploys the updated site.

Cloudflare can change dashboard labels; look for the equivalent settings if the interface differs. The configuration in `wrangler.jsonc` is the source of truth.

### Verify DNS, TLS and routes

Cloudflare handles TLS for a correctly attached custom domain. Check:

```bash
curl -I https://socialhub.win/
curl -I https://socialhub.win/studio
curl -I https://socialhub.win/tools
curl -I https://socialhub.win/privacy
```

Each existing page should return HTTP 200; static assets should also work. A shared preview needs a complete `/profile#p=...` link generated by Studio.

If you see **525 SSL handshake failed**, do not change random TLS settings or set SSL mode to Flexible. A 525 normally indicates that Cloudflare attempted TLS to an origin and the handshake failed. Confirm that the hostname is actually routed to your **Worker custom domain**, rather than an old proxied A/AAAA/CNAME record pointing to a non-Worker origin. Inspect **DNS → Records** and **Worker → Domains & Routes** together. Only after confirming the intended route should you remove stale/conflicting DNS entries.

If you see a redirect from `/studio.html` to `/studio`, that is expected: Cloudflare static assets support clean URLs. The homepage links directly to canonical paths.

## Manual deploy from a development machine

For maintainers with deployment access:

```bash
git clone https://github.com/SocialHub-Labs/socialhublabs.git
cd socialhublabs
npm ci
npm run check
npx wrangler login
npm run deploy
```

The site is static, so it does not need any Worker runtime secrets.

Do **not** commit Cloudflare API tokens, credentials, local `.dev.vars`, or environment files. For CI-based deployments use scoped secrets/settings outside version control.

## Local development

```bash
npm ci
npm run dev
```

Wrangler serves the local website and reports the development URL. In another terminal:

```bash
npm run check
```

A basic local smoke test:

```bash
curl -I http://127.0.0.1:8787/
curl -I http://127.0.0.1:8787/studio
curl -I http://127.0.0.1:8787/tools
curl -I http://127.0.0.1:8787/assets/core.mjs
```

Check in a real browser as well: Studio themes, link ordering, JSON import/export, share links, and both card sizes. JavaScript tests do not fully replace UI testing.

## Cost model and bot traffic

Static assets are served directly by Cloudflare without executing a Worker script. There is no server-side account or database that bots can consume or fill. This keeps the project within a free static-hosting model subject to Cloudflare's current limits and acceptable-use policies. Domain renewal is a separate expense.

The app deliberately does not include paid APIs, analytics trackers, background jobs or email-sending services. If a future version adds dynamic routes, reassess quotas, rate limits and abuse controls *before* deployment.

## Operational checklist

- Confirm domain, DNS and TLS work.
- Verify the GitHub source and issue links on the homepage.
- Configure/verify `hello@socialhub.win` before relying on email as a support channel.
- Test mobile layouts and keyboard navigation.
- Revisit [privacy](https://socialhub.win/privacy) before enabling analytics, cookies, external assets or backend storage.
- Check CI before merging updates.
- Check availability and routing after each deployment.
